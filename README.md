# Retail ETL

End-to-end ETL-пайплайн: читает выгрузку интернет-магазина, очищает и преобразует данные, загружает пять таблиц в PostgreSQL через SQLAlchemy и совершает 5 аналитических запросов для продуктовой команды.


## Что нужно

- Python 3.12–3.14 и поднятый локально PostgreSQL
- DBeaver или другой SQL-клиент
- Набор данных из папки data/


## Что лежит в проекте

| Путь | Что содержит |
|---|---|
| [src/__main__.py](src/__main__.py) | Запуск пайплайна |
| [src/extract.py](etl/extract.py) | Чтение CSV, XLSX, JSON, XML и выбор нужных полей |
| [src/transform.py](src/transform.py) | Очистка, преобразование типов, построение датафреймов и подготовка для импорта в БД |
| [src/load.py](src/load.py) | Подключение к PostgreSQL и запись готовых таблиц |
| [src/sql_execute.py](src/sql_execute.py) | Выполняет аналитические запросы и передает результаты основному модулю для выгрузки в CSV |
| [ddl/schema.sql](ddl/schema.sql) | Определения таблиц, типов и ограничений PostgreSQL |
| [sql/](sql/) | Пять аналитических запросов на SQL |
| [data/](data/) | Место для исходной выгрузки по умолчанию |
| [data/sql_results/](data/sql_results/) | Сюда осуществляется выгрузка результатов аналитических запросов в формате CSV |
| `logs/` | Файл логирования |
| [requirements.txt](requirements.txt) | Версии нужных библиотек |


## Запуск проекта

1. Сперва надо открыть терминал в корне репозитория (внутри папки project), т.е. где находятся папки  `src`, `data` и `ddl`. Далее надо распаковать архив с данными, т.е. `customers.csv`, `products.xlsx`, `orders.json`, `payments.csv` и `events.xml` прямо в папку [data/](data/README.md). Кроме этого, можно склонировать опубликованный репозиторий 

   ```bash
   git clone https://github.com/PypsenishAL/End-to-end-ETL.git
   cd End-to-end-ETL
   ```

2. Создаем виртуальное окружение и устанавливаем зависимости (я пользователь Windows, поэтому привожу как это сделать для это ОС):

   ``` python 
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   ```

3. Далее надо в DBeaver (или другой postgres-like редактор) подключиться к работающему серверу PostgreSQL и создать пустую базу `retail_etl`. Можно выполнить команду из подключения к базе `postgres` с включённым автокоммитом.

   ```sql
   CREATE DATABASE retail_etl;
   ```
   Глобально можно использовать любую другую уже имеющуюся базу данных и просто указать её название при основном запуске пайплайна.


   По умолчанию используется локальный PostgreSQL на порту `5432` с пользователем `postgres` и базой `retail_etl`. Список параметров показывает `python -m etl --help`. Если база или пользователь называются иначе, используй `--db-name` и `--db-user`. Для другого порта есть `--db-port`. Команды запускай интерпретатором из `.venv`, как в примере выше.

   Если исходники лежат в другой папке, укажи её через `--data-dir`. Например, `python -m etl --data-dir "./input files"`. Относительный путь в этом аргументе считается от текущей папки терминала.

4. Запуск пайплайна:

   ```bash
   python -m src
   ```

   В какой-то момент скрипт запросит пароль к базе данных. Если подключение или папка с исходными файлами отличаются от заданных по умолчанию, передайте параметры:

   ```bash
   python -m src --db-name retail_etl --db-user postgres --db-port 5432 --data-dir ./data
   ```
   Список параметров доступен через python -m src --help. CSV сохраняются в `data/sql_results/`, а журнал запуска — в `logs/etl.log`. Параметр --data-dir задаёт папку входных файлов.

## Что получится

| Таблица | Строк |
|---|---:|
| `dim_customer` | 700 |
| `dim_product` | 600 |
| `fact_order` | 1 200 |
| `fact_payment` | 949 |
| `fact_event` | 1 450 |

При повторном запуске данные в этих пяти таблицах полностью перезаписываются заново. Для проекта используется отдельная база. По умолчанию ищется база данных retail_etl, но при желании можно использовать любую другую, просто передав её название через `--db-name` при запуске.

| Запрос | Результат |
|---|---|
| `1_top_customers.sql` | Топ-10 клиентов по сумме завершённых заказов в каждой валюте |
| `2_monthly_revenue.sql` | Стоимость завершённых заказов по месяцу оформления и валюте |
| `3_popular_products.sql` | Популярность известных товаров по количеству проданных единиц |
| `4_top_users_last_activity.sql` | Дата последнего события пяти клиентов с наибольшим числом покупок |
| `5_users_without_orders.sql` | Клиенты без заказов любого статуса |

Покупкой считается заказ со статусом `completed`. Суммы в RUB, USD и EUR считаются отдельно. 
Пароль для БД запрашивается отдельно в терминале при выполнение скрипта.


## Модель данных и решения по качеству

Описание того, что представляет каждая строка таблицы и какие между ними связны, представлено далее:

| Таблица | Одна строка | Первичный ключ | Связи |
|---|---|---|---|
| `customer` | Клиент | `customer_id` | — |
| `products` | Товар | `product_id` | — |
| `orders` | Заказ | `order_id` | Клиент, товар |
| `payments` | Запись об оплате | `payment_id` | Заказ |
| `events` | Событие | `event_id` | Клиент, товар |

## Принятые решения по качеству и обработке данных

Далее я кратко опишу те решения по предобработке и трансформации данных, которые я принял в ходе реализации пайплайна:

1. Пробелы по краям значений убираются, а пустые строки считаются пропусками
2. Идентификаторы приводятся к целым числам в диапазоне PostgreSQL INTEGER. Для каждого собственного ID остаётся первая запись, прошедшая фильтры
3. Для товаров, заказов и платежей разрешены валюты RUB, USD и EUR

| Таблица | Что делается |
|---|---|
| `customers` | 	Записи без корректного ID или имени удаляются. Нераспознанная дата регистрации сохраняется как NULL |
| `products` | 	Записи с некорректным ID, пустым названием, неверной валютой или флагом активности удаляются |
| `orders` | 	Удаляются записи с некорректным ID, валютой, статусом, отсутствующей или нечисловой ценой, а также с отсутствующим, отрицательным или дробным количеством |
| `payments` | Удаляются записи с некорректным ID, датой или валютой, а также с отсутствующей, нечисловой или отрицательной суммой |
| `events` | Удаляются записи с некорректным ID, датой или пустым типом события |

Кроме этого, Если заказ или событие ссылается на отсутствующего клиента или товар, скрипт сохраняет саму запись и заменяет ссылку на NULL.
